# Finish the hosted demonstration

The services have different jobs: **Vercel hosts Next.js; Supabase supplies identity and PostgreSQL; Render runs the Python/FastAPI API**. Linking integrations does not deploy Python. This guide uses the existing Supabase database, not a second database on Render.

## Free Render service

1. Sign in at [Render](https://dashboard.render.com/). Import a new Blueprint from `Shikharyadav25/medi-bud-app`, branch `main`, using the root `render.yaml`. The definition requests only a **free** Docker web service in Singapore. Check the confirmation screen shows no paid resources. Do not add a disk or a new database.
2. Enter the required server secrets below in Render's environment settings. Never put them in Vercel's public variables, GitHub files or chat. The Blueprint intentionally cannot become ready with a fake database or missing encryption key.
3. Deploy. `/ready` must return HTTP 200 and `database_connected: true`; `/health` alone is insufficient. Keep demo authentication disabled. The container reads Render's `PORT` and has no access logs.
4. Set Vercel Production `NEXT_PUBLIC_API_URL` to the exact HTTPS Render origin (no `/v1` or `/api` suffix). Redeploy Vercel: public variables are compiled into its frontend. Keep the existing Supabase public integration variables.
5. Run `.venv/bin/python scripts/check_deployment.py https://YOUR-API.onrender.com`. This checks readiness, rejected anonymous report access and frontend/untrusted-origin CORS. It does not test live AI or authenticated user flows.

### Render settings

| Variable | Value/source |
| --- | --- |
| `DATABASE_URL` | Supabase **Connect → Session pooler** PostgreSQL URI, port 5432, with `?sslmode=require`. Use its real password, percent-encoded if it contains reserved URI characters. Session mode supports the API's transactions/advisory locks and IPv4-only hosts. Do not copy a Vercel transaction-pooler URI blindly. |
| `DATA_ENCRYPTION_KEY` | A Fernet key, generated locally using `.venv/bin/python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'`. Save privately and back it up; re-use it across redeploys. Do not use an arbitrary random string or rotate it on every deploy. |
| `SUPABASE_URL` | Already set in the Blueprint to this app's existing Supabase project. |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase legacy server/service-role JWT, server-only, needed for complete auth-identity deletion. Without it, deletion reports identity cleanup pending. Never use an anon/publishable key here. |
| `GEMINI_API_KEY` | Your Google AI Studio key, server-only; needed for live Gemini text and image analysis. Confirm the account's model access, quota and processing terms. |
| `SUPABASE_JWT_SECRET` | Only if the project's tokens use legacy HS256 signing. For asymmetric signing the API fetches the project's JWKS automatically. |
| `GROQ_API_KEY` | Optional additional server secret for text chat/fallback. Groq does not automatically replace the Gemini-dependent image extraction path. |
| `ALLOWED_ORIGINS` | Already set to `["https://medi-bud-app.vercel.app"]`. Add other actual deployed origins deliberately, not `*`. |

The API creates its encrypted runtime tables at startup and denies direct client-role access. Schema creation needs an appropriately privileged server database credential. Review the existing Supabase migrations and any existing records before applying changes; see [production.md](production.md). Do not point destructive integration tests at this database. No shared production demo token is enabled.

Free-service sleep/cold-start and provider quotas mean an instant/always-available demo cannot be guaranteed. Warm the API by opening `/ready` before presenting. Keep a loopback-only offline demonstration available using [demo_guide.md](demo_guide.md), clearly labeled; offline mode cannot demonstrate live AI/image or real signup. Do not use artificial keepalive traffic to evade provider limits.

## Hosted demonstration acceptance checklist

Use a real signed-in test account with **synthetic data only**. The presenter enters their own password and confirms their email. Do not treat mocked tests as these live checks.

- Signup, confirmation, login, logout, password recovery and account-switch isolation work on the deployed origin.
- Upload the synthetic PDF generated by the local demo, inspect the original, confirm its proposed values, and ask for hemoglobin: the answer cites the confirmed 14.2 g/dL. Unknown account data produces an honest limitation.
- Ask a general medical question with AI consent. Verify a real provider response, not just `ai_configured: true`. Test an unavailable/quota-limited provider without fake results.
- Upload a synthetic report/dish image with consent. Verify the image response; storing context remains explicit. Voice support is browser-dependent and is not a required demo guarantee.
- Save a profile, log water/sleep, add a reminder, create/download a plan, download a report, export data and reload. Redeploy the API and check saved data remains accessible with the same encryption key.
- Nearby care returns actual provider listings for a selected public area; unavailable directories show an honest error and external search links. Do not share personal GPS without permission.
- Verify account deletion only on an explicitly disposable test account after the other checks, with user approval. Check identity-deletion status instead of assuming success.

Only mark the hosted demonstration complete after these checks pass. Clinical production readiness, native mobile permissions and medical accuracy remain separate release gates.
